KubeTower {{ .Chart.AppVersion }} is installed as {{ .Release.Name }} in namespace {{ .Release.Namespace }}.

WHAT YOU JUST DEPLOYED
----------------------
The console's {{ if .Values.serverProfile }}server profile (no local shell, node shell or assistant){{ else }}desktop profile, local shell included,{{ end }}
running in a pod. NOT a multi-user console: whichever profile runs, everybody
who signs in shares one identity - this pod's ServiceAccount. Two people on it
at once are one user as far as the cluster is concerned.

1. REACH IT

   kubectl --context <your-context> -n {{ .Release.Namespace }} port-forward svc/{{ include "kubetower.fullname" . }} 5823:{{ .Values.service.port }}

   Then open http://127.0.0.1:5823
{{- if .Values.ingress.enabled }}

   An Ingress is enabled on:
{{- range .Values.ingress.hosts }}
     http{{ if $.Values.ingress.tls }}s{{ end }}://{{ .host }}
{{- end }}
   Everyone who can reach that host needs only the one password below.
{{- end }}

2. SIGN IN

   User: {{ .Values.auth.user }}
{{ if .Values.auth.existingSecret }}
   Password: whatever KT_PASSWORD_HASH in Secret {{ .Values.auth.existingSecret }} is the hash of.
{{- else if .Values.auth.passwordHash }}
   Password: whatever you hashed into auth.passwordHash.
{{- else }}
   No password was configured, so the binary drew one on first start and
   printed it once. Read it from the log:

     kubectl --context <your-context> -n {{ .Release.Namespace }} logs deploy/{{ include "kubetower.fullname" . }} | grep -i password

   It is printed once. {{ if .Values.persistence.enabled }}It is kept in the PersistentVolumeClaim, so a restart
   keeps it.{{ else }}persistence is OFF, so a restart draws a NEW one and the old is gone.{{ end }}
{{- end }}

3. WHAT WORKS AND WHAT DOES NOT, WITH THESE VALUES

   Reading resources ......... {{ if .Values.rbac.read }}yes{{ else }}NO - rbac.read is false, the lists will be empty{{ end }}
   Secrets and Helm releases . {{ if and .Values.rbac.read .Values.rbac.readSecrets }}yes - every Secret, this release's own session key included{{ else }}NO - those two pages will report a denial{{ end }}
   Custom resources .......... {{ if .Values.rbac.customResources }}yes (wildcard read is granted){{ else }}NO - rbac.customResources is false{{ end }}
   CPU/memory columns ........ {{ if .Values.rbac.metrics }}where metrics-server is installed{{ else }}NO - rbac.metrics is false{{ end }}
   Editing and deleting ...... {{ if .Values.rbac.write }}YES - treat it as cluster-admin, for everyone with the password{{ else }}no - rbac.write is false{{ end }}
   Pod shells, port-forwards . {{ if .Values.rbac.exec }}YES - a shell in any pod, for everyone with the password{{ else }}no - rbac.exec is false{{ end }}
   Node stats via kubelet .... {{ if .Values.rbac.nodeProxy }}YES - and the kubelet API with it: treat it as a shell on every node{{ else }}no - rbac.nodeProxy is false{{ end }}

4. CHECK IT CAME UP

   kubectl --context <your-context> -n {{ .Release.Namespace }} get pods -l app.kubernetes.io/instance={{ .Release.Name }}
   kubectl --context <your-context> -n {{ .Release.Namespace }} logs deploy/{{ include "kubetower.fullname" . }}

   /readyz is a real readiness signal: it goes unready when the kubeconfig
   stops reading or no context answers, not merely when the process dies.

5. BEFORE YOU SHARE THE URL WITH ANYBODY

   Do not. What makes this single-user is open work:

     * the port-forward cap is per process - 16 forwards for everybody at once
     * the session is stateless - revoking one person signs out all of them
{{- if .Values.serverProfile }}
     * (closed here) the local shell, the node shell and the assistant have no
       route at all under serverProfile
{{- else }}
     * the local shell and the Claude control are in this binary and their
       routes are registered - set serverProfile=true to remove them
     * the Claude control runs on one subscription, as one identity
{{- end }}
{{- if .Values.rbac.exec }}

   rbac.exec is ON in this release. Anybody who signs in has a shell in any
   pod in the cluster, holding this pod's ServiceAccount.
{{- end }}
{{- if .Values.rbac.write }}

   rbac.write is ON in this release. It lets the console create pods,
   Secrets and ServiceAccounts in every namespace, and a pod can be started as
   any ServiceAccount in its namespace - so anybody who signs in can act with
   the rights of any ServiceAccount in the cluster. On most clusters that
   reaches cluster-admin.
{{- end }}
{{- if .Values.rbac.nodeProxy }}

   rbac.nodeProxy is ON in this release. It reaches every kubelet's API, which
   Kubernetes' own guidance says allows running commands in the pods on each
   node. Anybody who signs in has that.
{{- end }}
{{- if and .Values.rbac.read .Values.rbac.readSecrets }}

   Reading Secrets includes this release's own. Anybody who signs in can read
   the session key from the Secrets page and mint a session that outlives a
   password change; only rotating the key ends it.
{{- end }}
